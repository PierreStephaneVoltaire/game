# Bri Virtual Pet — Balance, Autonomy, Shop, and Safety-Net Implementation Spec

**Status:** APPROVED IMPLEMENTATION SPEC  
**Source branch baseline:** `decay` @ `99c6962349925e1f9373b45d8f4a3d3e82600cb8` (`updated rules`, 2026-08-26)  
**Purpose:** Hand this file directly to a coding model. Treat requirements below as normative unless explicitly marked **Deferred** or **Measure before tuning**.

---

## 1. Product intent

This game is not a generic Tamagotchi. It is a Briatcookiebox-inspired companion simulation.

The player is responsible for care, but Bri is still an independent person. She can sometimes:

- eat something on her own;
- decide she is too tired and go to bed;
- read a book;
- watch/play something she owns;
- do a small piece of work and make money;
- improve her own mood;
- make a bad decision;
- have an accident;
- have a random health-related mishap;
- do something funny or productive without player input.

Autonomy is **not** an immortality system.

The intended relationship is:

> Player care is the primary survival/progression engine. Bri's autonomy makes the simulation feel human and occasionally softens mistakes, but long neglect still ends the run.

A player who disappears for roughly 3–4 days in Realtime should still be expected to reach terminal collapse through the existing death/depression path. Owning every useful room item must not turn a zero-input run into an immortal run.

---

## 2. Non-negotiable invariants

### 2.1 Neglect remains dangerous

- Full AFK is allowed to die.
- Roughly 3–4 days of no meaningful player care is expected to be terminal or extremely close to terminal.
- Automatic behavior may delay collapse, not indefinitely prevent it.
- The game must never auto-buy food for the player.
- Money generated by autonomous events must not automatically convert into survival resources.
- Care packages and autonomous actions must not recursively reset their own rescue eligibility.

### 2.2 Safety nets happen after consequences

Emergency autonomy is a **response to already-applied damage**, not pre-emptive protection.

For Food and Rest:

1. Need decay occurs.
2. Periodic Health resolution occurs.
3. Applicable Health damage is calculated and applied.
4. Only after damage is applied may the matching autonomous rescue run.
5. The rescue does not refund the Health that was already lost.

The player must feel the consequence of neglect even when Bri saves herself once.

### 2.3 One active activity at a time

The current single `state.activity` model remains authoritative.

- Bri cannot eat while sleeping.
- Bri cannot begin another time-consuming autonomous activity while already in an activity.
- A time-consuming item hook must require idle state.
- An instantaneous action may happen immediately before an activity begins, but must not occur while that activity is active.

### 2.4 No failure loops

A successful countermeasure must actually remove the failure condition that it is supposed to treat.

Examples:

- Hospital treatment must not discharge Bri into an immediate Kidney Stone re-onset from the same pre-Hospital feed history.
- Protein that successfully cancels a pending Sugar Crash must leave the rolling nutrition state below the crash trigger until new exposure changes it.
- Autonomous Rest must not repeatedly chain itself forever.
- Autonomous Snack must not repeatedly re-enable itself from its own Food gain.
- An injury event must respect a cooldown and may not re-roll continuously at every autonomous opportunity.

### 2.5 Deterministic gameplay randomness only

All new randomness must use the existing seeded RNG path.

- Never use `Math.random()`.
- Use stable `ruleId` and `rollId` names.
- Same state + same seed + same command/action context must produce the same outcome.
- Item event outcome tables must also be seeded.

### 2.6 Keep authored gameplay data separate from real nutrition facts

The repository already separates authored `nutritionScores` from sourced nutrition data. Preserve that design.

- Do not derive gameplay sugar/protein/salt/water scores from raw USDA/manufacturer data at runtime.
- Do not introduce a Hydration core metric.
- Existing authored `water`, `salt`, `protein`, `sugar`, and `caffeine` scores remain context values used by rules.

### 2.7 Do not hardcode the companion name into runtime logic

Continue using the configured companion profile and existing UI copy seams.

# PART A — SURVIVAL FAIRNESS

## 4. SURV-1 — Combined periodic need-damage cap

### Required value

Cap the combined periodic Health damage from critical:

- Food
- Rest
- Mood

to **2 Health per Health check**.

Kidney Stone, Sick, item injury, and other event damage are outside this cap.

### Resolution order

At each periodic Health boundary:

1. Calculate raw Food/Rest/Mood need damage independently.
2. Preserve the list of contributing need causes for diagnostics.
3. Sum the raw need damage.
4. Apply at most `2` Health damage.
5. Recovery ordering remains consistent with the current engine.
6. Apply external/non-periodic event/status damage separately.

### Damage-source accounting

The applied `HealthDamageSource.amount` values attached to the periodic event must sum to the Health actually removed by the capped periodic damage.

Do not report three `-2` sources if only `-2` Health was applied.

Use deterministic allocation:

1. Sort raw need sources by absolute raw damage descending.
2. Tie-break in stable order: `food`, `rest`, `mood`.
3. Allocate the capped damage across the ordered sources until the cap is exhausted.
4. A diagnostic-only field/event may preserve raw uncapped contributions if needed for simulation reports.

This prevents grave/death-cause output from implying more Health loss than actually happened.

### Config

Add/use a data-driven rule equivalent to:

```json
{
  "health": {
    "periodicNeedDamageCap": 2
  }
}
```

Use the repository's existing nesting conventions rather than forcing this exact JSON shape.

## 6. SURV-3 — Post-damage autonomous Food rescue

### Important architecture decision

**Autonomous Snack is NOT a normal weighted event-pool candidate.**

It is a post-damage rescue response.

If it competes with `none`, streams, care packages, room events, etc., the safety behavior can randomly fail to fire when it is specifically needed. Conversely, increasing its event weight enough to guarantee rescue would distort the ordinary event pool.

Implement it from the Health/damage reconciliation path or a dedicated post-health-boundary resolver.

### Eligibility

After a Health check has actually applied Food-related periodic damage, Bri may autonomously eat if ALL are true:

- `Food <= 2`;
- Food contributed to the Health damage at that boundary;
- there is no active activity;
- the Food rescue lock is not active;
- at least one owned food is eligible under ordinary feeding rules;
- Bri is alive.

### Food selection

Use existing feeding preference/refusal/nutrition semantics.

Eligible food should be selected deterministically using seeded RNG from:

- Liked food; or
- Variable food that would be accepted by the ordinary feeding path.

Do not auto-buy.

Do not conjure food.

Do not bypass:

- Sick restrictions;
- Full restrictions;
- nutrition history;
- Sugar Crash logic;
- Kidney Stone rolling history;
- authored item context.

Automatic eating should behave like a normal successful feed for nutrition/status consequences.

### Consequence ordering

The Food damage remains.

Example:

```text
Food critical
-> periodic Health -2 occurs
-> Bri autonomously eats an owned Uncrustables
-> Food increases
-> Health is NOT refunded
```

### Rescue lock

Food rescue is available **once per player-care episode**.

After an autonomous Food rescue succeeds:

```text
foodAutonomousRescueLocked = true
```

It remains locked even if:

- the autonomous snack itself raises Food above the safe threshold;
- Mom's Care Package adds food;
- another autonomous event changes Food;
- time naturally passes.

The Food rescue lock resets only when a **player-commanded care action** successfully raises Food to the safe reset threshold.

Initial proposed reset threshold:

`Food >= 5`

Examples that may reset it:

- explicit player Feed command resulting in Food >= 5;
- a player-commanded item action that genuinely raises Food >= 5.

Examples that MUST NOT reset it:

- autonomous snack;
- autonomous stream snack;
- care package;
- passive room effect;
- arbitrary time reconciliation.

If tests reveal `5` is too high/low, tune it in `simulation-rules.json`, not in code.

### Failure to rescue

If no food is owned, nothing happens.

If Bri is busy, the lock is not consumed. The rescue may be reconsidered after a later Food-damage boundary when she is idle.

A blocked rescue must not queue an infinite deferred action.

## 7. SURV-3R — Post-damage autonomous Rest rescue

Autonomous Rest should use the same safety philosophy as Food.

### Architecture change

The existing weighted `autonomous_nap` candidate must no longer be the primary critical-Rest safety mechanism.

Critical Rest rescue should be post-damage and deterministic in eligibility, not dependent on winning the general event lottery.

The ordinary event pool may still contain non-emergency naps if desired, but emergency Rest is separate.

### Eligibility

After a Health check has actually applied Rest-related periodic damage, Bri may autonomously begin Rest if ALL are true:

- `Rest <= 2`;
- Rest contributed to Health damage at that boundary;
- no activity is active;
- the Rest rescue lock is not active;
- Bri is alive.

### Behavior

- Start the normal Rest activity.
- Preserve normal time cost.
- Preserve ordinary Rest completion rules.
- The triggering Health damage stays applied.
- Autonomous Rest must not count as player care.

### Rescue lock

After autonomous emergency Rest begins:

```text
restAutonomousRescueLocked = true
```

The lock is reset only by a later **player-commanded** Rest/care action that restores Rest to the configurable reset threshold.

Initial proposed threshold:

`Rest >= 5`

The autonomous Rest activity completing above 5 does **not** unlock another autonomous Rest.

This is the anti-immortality rule.

### Food + Rest on the same boundary

Food and Rest locks are independent, but actions may not overlap.

If both rescue conditions become eligible at the same Health boundary:

1. Resolve the instantaneous autonomous Snack first if possible.
2. Re-check that no blocking activity exists.
3. Then begin autonomous Rest if still eligible.
4. Once Rest begins, no food action may occur until Rest ends.

This permits "she grabbed something and then went to bed" without allowing eating during sleep.

## 8. SURV-4 — Low-Health Mood spiral cooldown

Keep the low-Health Mood penalty.

When Health is within the current critical range (currently 1–8), stat changes that qualify for the existing low-Health Mood penalty may produce at most:

`Mood -1 per 12 game-hours`

Use one global timestamp/cooldown, not one cooldown per changed metric.

Suggested state:

```ts
history.lastCriticalHealthMoodPenaltyAt: number | null
```

Rules:

- Health recovering above 8 does not erase the historical timestamp.
- Multiple qualifying changes at the same simulation timestamp can produce at most one penalty.
- The cooldown uses game time.
- The event must remain narrated/traceable.

# PART B — AUTONOMY AS A GENERAL SYSTEM

## 9. Separate three kinds of autonomy

Do not treat all automatic behavior as the same mechanic.

### 9.1 Emergency safety response

Examples:

- autonomous Food rescue;
- autonomous Rest rescue.

Properties:

- triggered from damage/state resolution;
- not weighted against unrelated events;
- finite/locked;
- intended to slow collapse.

### 9.2 Ordinary autonomous life event

Examples:

- reads a book;
- watches something;
- plays a game;
- messes with Socks;
- goes for a tiny walk;
- has a random good mood moment;
- gets lightheaded;
- hurts herself using something incorrectly.

Properties:

- participates in the ordinary weighted event system;
- uses cooldowns;
- may have positive, neutral, or negative outcomes;
- does not bypass active-activity constraints.

### 9.3 Scheduled/system event

Examples:

- Sugar Crash deadline;
- medical payment;
- status recurrence;
- Kidney Stone natural passage.

Properties:

- timeline-driven;
- not part of weighted random opportunities.

Keep these paths distinct.

## 10. Extend automatic item hooks enough to support real autonomy

Current automatic hooks support:

- `weight`;
- one `message`;
- `owned` / `placed`;
- metric effects;
- cooldown.

Extend them rather than creating one-off hardcoded handlers for every item.

### Required additional capabilities

Add optional fields conceptually equivalent to:

```ts
type AutomaticEventHookDefinition = {
  id: string;
  weight: number;
  message?: string;
  messages?: string[];
  eligibility: 'owned' | 'placed';

  effects?: Partial<Record<MetricName, EffectRange>>;
  balanceEffect?: EffectRange;

  cooldownHours?: number;
  sharedCooldownKey?: string;

  requiresIdle?: boolean;

  outcomes?: Array<{
    id: string;
    weight: number;
    message: string;
    effects?: Partial<Record<MetricName, EffectRange>>;
    balanceEffect?: EffectRange;
    healthDamage?: {
      min: number;
      max: number;
      causeId: string;
      causeName: string;
    };
  }>;
};
```

This is a conceptual contract. Match repository naming/style.

### Backward compatibility

Existing hooks must continue working without modification.

If `outcomes` is absent:

- use the existing direct hook behavior.

If `outcomes` exists:

1. choose exactly one outcome using seeded RNG;
2. apply its metric effects;
3. apply its balance effect through `creditIncome` when positive;
4. apply explicit event Health damage outside the periodic-need cap;
5. write the selected outcome to the event ledger.

### Shared cooldowns

`sharedCooldownKey` exists to prevent stacking multiple similar objects into unrealistic autonomous spam.

Examples:

- multiple reading objects can share `autonomous_reading`;
- multiple small work hooks can share `autonomous_side_gig`;
- related kitchen-accident hooks can share `kitchen_accident`.

Store shared cooldown timestamps in the existing `history.eventCooldowns`.

### Idle requirement

For new hooks that imply Bri is actively doing something:

```text
requiresIdle = true
```

Examples:

- reading;
- gaming;
- side work;
- walking;
- risky cooking behavior.

Pure room-observation events can retain current behavior unless deliberately changed.

# PART G — SUGAR CRASH

## 23. Replace one-shot protein clearing with rolling accumulated interaction

The intended model is accumulated nutrition over the same rolling window.

### Window

Use the existing rolling Sugar Crash window:

`6 game-hours`

### Authored values

Use each successful consumption's authored:

- `sugar`
- `protein`

scores.

### Net sugar exposure

Calculate:

```text
totalSugar = sum(sugar scores in rolling 6h)
totalProtein = sum(protein scores in rolling 6h)
effectiveSugar = max(0, totalSugar - totalProtein)
```

This is the initial 1:1 authored-score counteraction rule.

### Crash threshold

Schedule Sugar Crash when:

`effectiveSugar >= 4`

and no crash is already active/pending.

### Atomic food evaluation

For one consumed item, apply all of its nutrition components before testing the final `effectiveSugar`.

Therefore, an item with enough protein relative to its sugar can partially or fully cancel its own sugar contribution.

Do not:

1. see sugar;
2. schedule crash;
3. then see protein;
4. leave a stale scheduled crash.

### Pending crash cancellation

If a crash is pending and a later consumption causes:

`effectiveSugar < 4`

then:

- clear `sugarCrashDueAt`;
- remove the visible pending warning/timed effect;
- write a Journey/system event explaining the crash was averted if appropriate.

### Active crash clearing

If an active `sugar_crash` exists and subsequent protein changes the rolling balance below the threshold, the current authored protein-clearing behavior may clear it.

### No immediate reschedule loop

Do not delete arbitrary consumption history merely to suppress re-triggering.

Because protein remains inside the same rolling window, `effectiveSugar` remains below threshold after cancellation.

A new crash can schedule only if:

- new sugar enters the window; or
- older protein expires from the window while enough sugar remains, if the timeline rules explicitly reconcile this boundary.

If the latter is implemented, it must be chronological and deterministic.

The same unchanged state must never repeatedly:

`cancel -> immediately schedule -> cancel -> schedule`

at one timestamp.

# PART I — HOSPITAL AND MEDICAL PAYMENT PLAN

## 29. Replace Hospital lump-sum balance destruction with medical obligations

The current Hospital billing path immediately charges the current Hospital cost into `balance`.

Change this.

Hospital should create a medical payment-plan obligation instead.

Do not use the previously proposed lifetime-income sliding-scale design in this implementation.

### Existing principal

Preserve the current configured Hospital principal amounts unless separately changed:

- uninsured principal: current `medicalCare.cost`;
- insured principal: current `medicalCare.insuredCost`.

Do not invent a new principal in code.

### Coverage lock

Insurance status is determined when the Hospital activity starts and stored in the activity payload/bill.

Buying insurance after the visit starts does not retroactively change that visit's bill.

For this pass, preserve the current Insurance Card consumption semantics unless the existing code/data is independently changed.

---

## 30. Medical debt state

Do not overload negative `balance` to represent the payment plan.

Add explicit state.

Suggested type:

```ts
type MedicalDebtBill = {
  id: string;
  createdAt: number;
  originalPrincipal: number;
  remainingPrincipal: number;
  scheduledDailyPayment: number;
  insuredAtStart: boolean;
};
```

Suggested `GameState` addition:

```ts
medicalDebt: MedicalDebtBill[];
```

Initialize it empty.

### Why separate state

The payment plan is not the same thing as having negative cash.

This preserves:

- ordinary shop money;
- existing negative-balance debt behavior if some other system creates it;
- the feedback requirement that the payment plan itself should not hard-lock Health recovery.

---

## 31. Daily scheduled payment

Initial configured payments:

- uninsured: `$150/day`;
- insured: `$25/day`.

Process once per local calendar day.

For each outstanding bill, oldest first:

```text
due = min(scheduledDailyPayment, remainingPrincipal)
available = max(0, balance)
paid = min(due, available)
balance -= paid
remainingPrincipal -= paid
```

If the player cannot cover the full scheduled payment:

- do not create new negative cash from the missed payment;
- leave unpaid principal outstanding;
- emit at most one clear Journey line for that day;
- do not deal Health/Mood damage for missing the payment.

Remove fully paid bills.

### Multiple bills

Multiple outstanding bills are allowed.

Process them oldest first.

If tests show paying each bill's full minimum on the same day is too punitive, tune the data/rule later. Do not silently collapse bills in a way that loses principal history.

---

## 32. Shop service: Pay Medical Debt in Full

While total medical debt is greater than zero, the Shop must always expose a conditional service:

**Pay Medical Debt in Full**

This is not ordinary rotating stock.

### Visibility

Always visible while:

`sum(remainingPrincipal) > 0`

Hidden otherwise.

### Price

Apply a 15% discount:

```text
fullPrice = ceil(totalRemainingPrincipal * 0.85)
```

### Purchase behavior

If `balance >= fullPrice`:

- subtract `fullPrice`;
- clear all outstanding medical bills;
- record a purchase/payment event;
- narrate the discount/payment clearly.

If the player cannot afford it:

- reject normally;
- do not partially pay;
- do not add it to inventory;
- do not remove it from the conditional Shop.

### Purpose

Early game:

- the player can survive Hospital without instantly losing $10k cash.

Late game:

- a rich player has a reason to clear the obligation immediately for a meaningful 15% discount.

---

## 33. Existing debt recovery penalty

The current negative-balance recovery penalty remains a separate mechanic.

If negative balances remain possible, reduce its cap:

`3 -> 2`

Medical payment-plan principal does **not** automatically count as negative `balance` for this recovery penalty.

Do not add the proposed Financial Ruin ending in this implementation.

## 35. Soft cap active stream contributions

Use a soft cap.

At each natural audience-growth tick:

1. collect non-expired active stream contributions;
2. sort by `startedAt` ascending;
3. stable tie-break by contribution ID;
4. first 4 contributions count at 100%;
5. every contribution after the first 4 counts at 25%;
6. sum the weighted values;
7. round the final growth value once.

When an older contribution expires, the next contribution automatically moves into the full-value group.

This preserves:

> More streaming always helps a little.

while preventing the Optimal profile from stacking nine+ full seven-day boosts.

### Data values

```text
fullValueBoostCount = 4
excessBoostMultiplier = 0.25
```

Put them in simulation/progression rules.

# PART T — FINAL DEFINITION OF DONE

This feature set is complete when all of the following are true:

1. Need stacking is capped without corrupting damage attribution.
2. Food pressure is reduced to the approved rate.

## Final implementation philosophy

Do not optimize for "protect the player."

Optimize for:

> **Bri has agency, care matters, neglect hurts, and the simulation never traps the player in a nonsensical loop.**

Good player care should reliably work.

Bad luck may create stories.

Bri may occasionally rescue herself.

Bri may occasionally create her own problems.

But if the player abandons her, the game should not quietly play itself forever.
